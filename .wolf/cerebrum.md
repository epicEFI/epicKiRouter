- [2026-09-12] Oracle pins have three failure modes, all seen in M1a reviews: (1) memory-reconstructed expectations instead of jar-captured values (bug-045); (2) degenerate inputs where the terms under test cancel — e.g. fast-path pins at x=0 can't catch sign swaps (T5 gap 1, T6 finding 1); (3) pins that never execute the branch they claim to cover — e.g. a T17 bug-compat pin whose geometry takes the other branch (T6 finding 2). For every pin: capture from the oracle, choose inputs where the mutated terms differ, and confirm the branch actually runs.
- [2026-09-12] Two more pin failure modes found in M1b Tasks 1-2: (4) anchor-blind agreement — pinning only the input form where a wrong implementation coincidentally matches the oracle (`(string_quote ')` matched while `(string_quote 'a)` diverged; IGNORE_QUOTE bug, Task 1 review). Pins must include a form where wrong and right differ. (5) capture-tool rounding — Java `FloatPoint.toString()` rounds to 4 fraction digits, so pinning through it records a rounded lie (`7` vs exact `7.000000000000002`); capture doubles via `Double.toString`/raw bits, never through a formatting toString.
- [2026-09-14] Wedge false-positive: a subagent transcript frozen for ~3 min is NOT proof of a wedge — a long model-generation turn or a minutes-long cargo/gates run looks identical in its first minutes (Task 9 spec review: 3-min freeze, then 108KB→370KB growth on re-sample). Before TaskStop + re-dispatch, take a SECOND size sample after a ~4 min grace interval; growth = healthy. Also: pins never land in the digest warnings surface from FRLogger sites — the D12 parity warnings list is fed ONLY by `Wiring.java`'s `warnings.add` sites via `ReadScopeParameter.warnings` (Task 6 jar correction); every other FRLogger.warn is log-only and wiring `push_warning` there breaks WARN_COUNT parity.
- [2026-09-14] Pin failure mode (6), found in the M2 T3 fix round: a MEMOIZED oracle accessor makes RE-QUERYING the same object pin the CACHE, not the code path. `Pin.getShape` memoizes the whole shape array on first call (`precalculatedShapes`, Pin.java:170-236), so re-querying one pin after flipping `flipStyleRotateFirst` returned byte-identical cached shapes (verified empirically) — a "both styles" pin built on re-query passes even with the mirror-order port wrong. Fix: insert a FRESH object under the changed flag/table (SPIKE3 vs SPIKE2) and check for cache-memoizing fields (`precalculated*`, set-once caches like `Pin.getCenter`'s `setCenter`) before designing a re-query pin.
- [2026-09-14] Pin failure mode (7), found in the M2 T8 quality review: an EQUALITY pin (`dispatch == plain branch`) is blind when the two compared paths COINCIDE on the pinned input — an inverted flag, a wrong flag source (manager vs tree), and an always-plain port all pass. A pin asserting two paths agree needs a CONTRAST witness that disagrees on the same input (`dispatch == plain != core`), and a flag-source pin needs an input where the two candidate flags DIFFER (autoroute class-1 tree with compensation off: tree flag true, manager flag false). Sharpening of mode (4) for dispatch/equality-shaped pins.
- [2026-09-15] Pin failure mode (8), found in the M2 T10 contacts round: a pin literal RECONSTRUCTED from a capture's narrative (assumed trace 1372 had 2 corners because M_PAIR described an endpoint-on-mid-corner pair) failed against a faithful port — the capture row pinned only first/last (`M_Y 1372 0 first=... last=...`), the DSN wire is 3-corner, and `(type protect)` = USER_FIXED makes normalizeAllTraces a no-op there. Rule: every expected value must be a LITERAL capture row; when a capture shows only part of a structure, pin only that part. Related: pins asserting ABSOLUTE ids of post-parse insertions must replay the oracle's FULL insertion sequence (alloc is monotone — skipping earlier inserts shifts every id).
- [2026-09-15] Pin failure mode (9), found in the M2 T15 quality review: a SELECTION pin (`first-qualifying-drill-wins`) is blind when the pinned input's candidate behaviors COINCIDE — with ONE qualifier + a fall-through, the last-qualifier mutant (M8: walk all drills, remember the last, quirk intact) returns the same verdict and survives every gate. A selection/order pin needs an input where the alternative selection rules actually DIFFER (TWO qualifiers with different centers: first=(2000,0) vs last=(1500,0)). Extension of mode (7) from equality pins to winner-selection pins; the doc comment must not assert "both qualify" unless the vector makes it true.

- [2026-09-16] Pin failure mode (10), found in the M3-T5 review round: an OBSERVABILITY pin (call-count/witness assertion on a seam) is VACUOUS when the fixture pre-seeds the state that short-circuits the observed seam — the reset-keeps-memo pin seeded a complete tree room covering the page, so `calculate_expansion_rooms` reused it and the completion seam never fired, making `complete_calls.is_empty()` true even during a full recompute; the invalidate-in-reset mutant SURVIVED (caught only by the mutation re-run, not by review). Rule: a pin that counts calls to a seam must leave the fixture's tree EMPTY of the state that bypasses that seam, and every "zero calls"-style pin must be mutation-verified (a green pin proves nothing about its own discriminating power).
- [2026-09-18] Pin failure mode (11), found in the M3-T9 re-review: an IDENTITY pin (`wrapper == !core(wrapper')`) asserts the refactor's own structural invariant, not the Java behavior — when the refactor itself is the bug, the pin is a tautology that cannot fail. The trigger: two Java "mirror" functions (FromDoor/ToDoor horizontalFirst, FoundConnectionLocator45Degree.java:48-101 vs :304-356) were structuralized as `core` + strict negation, but Java's faces are COMPLEMENT OFF-TIE, AGREEMENT ON TIE (`h >= w` vs `h <= w` — both TRUE at h==w); the negation flipped five tie arms (diagonal |dx|==|dy| doors are ordinary in default 45° mode on integer coordinates). Rules: (a) never assert `A == !B` between two ported functions as a parity pin — pin each face against JAVA's own verdicts at tie inputs specifically; (b) before structuralizing two similar Java functions as shared-core-plus-transform, diff them arm-by-arm AT THE TIE BOUNDARIES, not just the branch structure — mirror pairs in this codebase agree at ties more often than they strictly complement; (c) a refactor of already-verbatim-Java code carries the same parity risk as a fresh port and needs the same witness (run the new pins against the PRE-refactor code to witness them failing-or-passing honestly).
- [2026-09-19] Pin failure mode (12), found in the M3-T10b fix round (buglog 147): a RECURSION-HEALS blind spot — a mutant in an early decision (springOver's containment direction) survives every pin run at the public/default recursion budget because downstream wrap recursion converges back to the same final circuit, "healing" the wrong intermediate pick. Only a pin at a BUDGET BOUNDARY the production caller actually exercises (the instance check's decremented depth-1 re-entry) discriminates — there the budget burns on the wrong inner obstacle and the divergent one surfaces at depth 0. Compounding errors in the original world design: (a) obstacle-class assumption unverified (a SHOVE_FIXED via is *routable* per Via.java:147-149 and can never be the second springOver obstacle — the world needed USER_FIXED); (b) depth-20 observability vacuity (final-geometry-only assertion at the default budget). Rules: (a) when pinning a decision that feeds recursion, run the discriminating input at a REDUCED budget the Java caller really passes, not just the public default; (b) verify the fixture's item-class semantics against the Java gate (`isRoutable`/fixed-state ladders) before assigning it a role; (c) a pin whose world survives its own correction mutant at the default budget is observability-vacuous even if green — mutation-verify at every budget face the pin claims.
- [2026-09-21] Pin failure mode (13), found in the M3-T17a spec-review round (SR-3/SR-4): SELECTED-ARM VACUITY — when a capture corpus already holds a discriminating row and the pin pins only the non-crossing rows, every arm is green while the seam is unobservable (P1b pinned S1=unfixed×false and S2=fixed×true; neither crosses flag × shovability, so the delegation's flag passthrough could be replaced by a literal `false` and all pins stayed green — the `S1_unfixed_true` row existed in the T11 capture all along). Same round, the PRODUCTION-trait-impl blind spot: a pin through a TEST-HARNESS impl of a trait does not observe the production impl the battery routes through (P4 drove drill/pins.rs's Harness `via_center`; the engine.rs production impl was swapped to `pin_center` and nothing died). Rules: (a) when a pin's world has a 2×2 discriminator (flag × property, kind × net, …), pin at least one arm from EVERY row and column — the crossing cell is the pin; (b) verify an existing capture holds the crossing row BEFORE crafting a new world (grep the captures/ dir — the oracle answer may already be on disk); (c) a trait with multiple impls needs its pin driven through EACH impl the callers actually use — a shared-craft pin parameterized over impls, or one pin per impl.

- [2026-09-22] Gate failure mode (14), found in the M4-T2 spec review (buglog 182): an ALL-TARGETS BLINDSPOT — `cargo clippy` WITHOUT `--all-targets` never lints `#[cfg(test)]` modules, so a test-only diff sails through a green gate that cannot see it (T2's committed tree failed the exact CI invocation with exit 101 while the report claimed exit 0; only the reviewer's own run caught it, one push away from a broken rust-check.yml). Compounding: the exit was first read after a `| tail` pipe — the `$status`-after-pipe trap again. Rules: (a) run every gate in the dispatch's EXACT form — flags are load-bearing, not style; (b) for test-only diffs assume the default clippy face is blind and verify with `--all-targets` unpiped, capturing the real exit (never read it through a pipe); (c) review-fix rounds must re-run gates themselves with the same exactness they demand of the implementer.
- [2026-09-22] Two documentation/pin-granularity modes, found in the M4-T3 spec review (SPEC_COMPLIANT_WITH_MINORS, fix commit acd8ebf3f): (15) CITATION DRIFT — call-site line numbers and stage labels cited into durable docs (SEAM.md, task report, commit message) from pre-commit working notes were stale by the time they landed (cited :199/:218/:369/:383 + batch.rs:784 + "fanout/escape"; actual :209/:236 inside `route` / :394/:411 inside `retry_connection_necked` + batch.rs:807; Rust has no fanout stage until T7). Line numbers shift with every edit pass (fmt, refactor); re-verify them against the COMMITTED tree immediately before writing the report/SEAM, not from memory of an earlier segment. A landed commit message cannot be fixed — only erratum-ed in live docs (T1 precedent). (16) MEASURED-NOT-PINNED boundary — a boundary measured by a scan (regionscan x* = 992250) but pinned only via worlds far inside/outside lets a ±1-unit drift of the formula survive the whole pin set (reviewer T3-S4: offset 6750→6751, 8/8 green). When a pin set's discrimination depends on a closed-form boundary, add the EXACT-boundary world ±1 unit (the inclusive edge itself and one step either side) and mutation-verify both directions (T3-M5: +1 and −1 both killed).
- [2026-09-24] Gate failure mode (17), found in the M4-T11 spec review (MINOR-3, live-witnessed during the R1 mutant re-run): a STALE-BIN FALSE GREEN one layer up from the buglog-184 family — `cargo test -p epic-harness` rebuilds the TEST binary but does NOT relink the spawned `target/debug/epic-harness` bin, so an e2e pin that shells out to that bin silently judges PRE-edit code and a genuinely-killable mutant PASSES (bin mtime 14:39 vs test binary 15:08 during the review). Any pin that spawns a built bin (e2e smokes, gate-mode checks) must be judged only after `cargo build -p <bin-crate>` for EVERY crate whose source the pin exercises — test-binary freshness is NOT bin freshness. The canonical precondition is documented on `e2e_built_harness_bin` (router_compare.rs); before trusting an e2e result after a harness-source edit, compare the bin's mtime against the newest source file it links.
- [2026-09-28] Aggregate-adoption trap (18), found in the M6-T10 spec review (MINOR-1): the coordinator re-derived Tier A's Σ personally (matched exactly, 2075.7) then adopted B's and C's Σ straight from the harness summary lines — the first match created false confidence the summary was per-fixture by construction. It was NOT: the battery summary "in Ns" is whole-loop elapsed including in-process detail-localizer re-routes on red non-killed fixtures (router_compare.rs:1899/:2085-2092 vs per-fixture :799-810, guard :2160-2168), so B-ON carried a 776.5 s undisclosed gap (3817.5 vs 3041.0) that only the reviewer caught. Rule: EVERY adopted aggregate is reconciled against its constituents (sum the per-fixture fields, compare to the summary), not just the first one; a summary-vs-sum divergence is itself a finding about what the summary measures.
- [2026-09-30] Constant-adoption trap (19), found in the M8 milestone adjudication (F-ADJ-1, adjudication-report.md): at M8-T8 the coordinator re-derived all 24 judgment-cell APPLICATIONS by hand but took one band CONSTANT's derivation on faith (AM2's via_density band 2.4752; the declared gap-of-means base is 1.5752 — bend's band 2.6488 matches its own gap exactly, proving the intended law; the adopted 2.4752 matches no recorded face). The cell applications were all exact; the CONSTANT silently changed the criterion verdict (letter PASS → REGRESSION-FINDING). Rule: every adopted CONSTANT (threshold, band, budget, version) gets its DERIVATION re-checked against the committed record in writing at adoption — re-deriving where a constant is USED is not evidence for where it came FROM. Banked as an M9-plan opening rule (2026-09-30-epicrouter-m9-gui.md).
